One design decision to be aware of
The optimistic lock retry is handled differently in two places intentionally:

InventoryService.restock() — uses REQUIRES_NEW so each retry commits in its own transaction. Safe for REST callers.
SagaInventoryService — uses saveAndFlush() inline so the version check fires immediately within the same transaction boundary. This keeps the entire saga step (all items + outbox write) atomic in one commit, which is the correct saga contract.

Implementation Plan — Inventory Service
Problem Statement
Build the inventory-service microservice for the ecommerce platform. It manages stock levels per product, exposes three REST endpoints (stock read, availability check, admin restock), participates in the Order saga as a Kafka command consumer (reserve/confirm/release), publishes saga replies and domain events via the transactional outbox pattern, and auto-initializes stock entries when product events arrive.

Requirements
REST API (behind API Gateway, auth via X-User-Id/X-User-Roles headers):

GET /inventory/{productId} → StockResponse{productId, availableQty, reservedQty} — User
GET /inventory/{productId}/availability?qty=N → AvailabilityResponse{productId, available} — Internal (Feign from Cart)
PUT /inventory/{productId} — Admin restock, body StockUpdateRequest{quantity}
Kafka consumers (group: inventory-service-group):

inventory.reserve.command → reserve stock for all items in an order; reply on inventory.reserve.reply
inventory.confirm.command → convert reservation to actual deduction; reply on inventory.confirm.reply
inventory.release.command → release (cancel) a reservation; reply on inventory.release.reply
product.created / product.updated → auto-init/upsert stock_items row
Transactional outbox for all Kafka replies (same pattern as product-service)

Optimistic locking (@Version on stock_items) with retry-with-backoff on conflict

Consumer-side idempotency via processed_event table

Database: inventory_db with tables stock_items, stock_reservations, processed_event, outbox_event

Port: 8083, context path /api/v1, Eureka registered as inventory-service

No Redis — no cache needed for inventory (stock values change frequently)

Background
From the existing codebase:

Security uses GatewayAuthFilter (reads X-User-Id/X-User-Roles headers forwarded by the gateway) — no JWT library needed
Outbox: OutboxEvent entity + OutboxRelayService (@Scheduled, PESSIMISTIC_WRITE + SKIP_LOCKED) + KafkaConfig — identical to product-service
Exceptions: AppException hierarchy + GlobalExceptionHandler — copy from product-service
MapStruct for entity ↔ DTO mapping, Lombok throughout
pom.xml mirrors product-service dependencies (Spring Boot 3.2.5, Java 21, Spring Cloud 2023.0.1)
ddl-auto: validate — schema is provided by db-init.sql, not generated by Hibernate
No Redis dependency in inventory-service (unlike product-service)

Task 5: Optimistic lock retry wrapper

Objective: Implement a reusable retry-with-backoff decorator for optimistic locking conflicts, used by all saga command handlers and the restock endpoint.
Implementation:
Create OptimisticLockRetryHelper component (or use Spring Retry):
Method: <T> T executeWithRetry(Supplier<T> operation, int maxAttempts, long initialBackoffMs) — catches ObjectOptimisticLockingFailureException, sleeps with exponential backoff (initial * 2^attempt), retries up to maxAttempts (default 3). If all attempts exhausted, throw ConflictException("Stock update conflict after retries — please retry the request").
Configure defaults: maxAttempts=3, initialBackoffMs=50 (fast for saga commands).
Wire into InventoryService.restock() and all saga handler methods in Task 6.
Tests: Unit test OptimisticLockRetryHelper — mock Supplier that throws ObjectOptimisticLockingFailureException twice then succeeds; verify it returns the value on the 3rd attempt. Mock that throws 4 times; verify ConflictException is thrown.

Task 6: Saga command consumers (reserve / confirm / release)

Objective: Implement the three Kafka consumers that drive the Order saga's inventory steps, with idempotency, outbox replies, and retry on optimistic lock.
Implementation:
SagaInventoryService (or extend InventoryService) with three transactional methods:
reserve(orderId, List<{productId, qty}>):
For each item: load StockItem, check availableQty >= qty (if any fails → prepare a FAILED reply payload and return early).
If all pass: for each item deduct availableQty -= qty, increment reservedQty += qty, save (via retry helper). Create a StockReservation(status=RESERVED) per item.
Write outbox event inventory.reserve.reply with {orderId, status:"SUCCEEDED", reservationIds:[...]} or {orderId, status:"FAILED", reason:"INSUFFICIENT_STOCK", productId}.
confirm(orderId):
Find all StockReservation by orderId with status RESERVED.
For each: decrement reservedQty -= qty on StockItem (via retry helper), set reservation status=CONFIRMED.
Write outbox event inventory.confirm.reply with {orderId, status:"SUCCEEDED"}.
release(orderId):
Find all StockReservation by orderId with status RESERVED.
For each: increment availableQty += qty, decrement reservedQty -= qty on StockItem (via retry helper), set reservation status=RELEASED.
Write outbox event inventory.release.reply with {orderId, status:"SUCCEEDED"}.
InventoryCommandConsumer — one @KafkaListener per topic (or a single class with three methods):
Deserialise the envelope JSON using ObjectMapper.
Extract eventId from the envelope; check processedEventRepository.existsById(eventId) — if true, log and skip (idempotency).
Call the appropriate SagaInventoryService method (which handles the DB work + outbox write in one transaction).
In the same transaction (or just after): save a ProcessedEvent(eventId, now()).
Consumer error handling: @KafkaListener with a DefaultErrorHandler (dead-letter or log-and-continue for non-retryable deserialization errors).
Outbox reply payload shapes match the event catalog exactly.
OutboxRelayService + KafkaConfig wired for Kafka producer (from Task 1/3) — replies flow out via the outbox.
Tests:
Unit tests for SagaInventoryService: mock repositories; verify reserve deducts available qty, writes correct outbox payload; verify reserve with insufficient stock writes FAILED reply without touching stock; verify confirm and release correctly update qty and reservation status.
Integration test for InventoryCommandConsumer using @EmbeddedKafka: send a inventory.reserve.command message → consume → verify stock_items qty changed + outbox_event row written + processed_event row written. Send the same message again → verify it is skipped (idempotency).
Demo: With Order Service running, place an order via the API Gateway. Observe in Kafka UI that inventory.reserve.command arrives → inventory.reserve.reply is sent. Order saga proceeds to payment step.
Task 7: Product event consumer (auto-init stock)

Objective: Listen to product.created and product.updated to automatically initialize or update stock_items rows, so inventory is self-consistent with the product catalog without manual admin intervention.
Implementation:
ProductEventConsumer (@Service, @KafkaListener(topics={"product.created", "product.updated"}, groupId="inventory-service-group")):
Deserialise envelope, extract eventId for idempotency check.
From payload extract productId and active flag.
On product.created: if no StockItem exists for productId, create one with availableQty=0, reservedQty=0. If one already exists (e.g. Admin already restocked), do nothing.
On product.updated: if active=false (product deleted/deactivated), log a warning but do NOT remove the stock item — existing reservations may still reference it and the saga must be allowed to complete.
Both paths: save ProcessedEvent in same transaction.
Idempotency via processedEventRepository as in Task 6.
Tests:
Unit test ProductEventConsumer: send a product.created payload → verify StockItemRepository.save is called with availableQty=0; send the same event again → verify save is NOT called again (idempotency). Send product.updated with active=false → verify no deletion occurs.
Integration test (@EmbeddedKafka): publish product.created → verify row in stock_items.
Demo: Create a product via Product Service. Observe that inventory-service automatically creates a stock_items row with available_qty=0 in inventory_db (check via psql or Swagger GET /inventory/{productId}).
